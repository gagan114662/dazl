# #346 contact-identity fixes: acceptance evidence

**Status: stubbed run done; the live user journey is NOT yet shown.** The 58 passing unit tests are not acceptance. This file gives (1) the exact live steps Instinct (or the owner) can run on a deployed instance and what to look for, and (2) the captured output of a stubbed run of the same flows from the real code (`346-stubbed-output.txt`, regenerated by `scripts/acceptance-346.mts`).

## What #346 changed (on main as c30f2a3)
1. A contact/company record from Apollo, People Data Labs or a crawled site attaches only when its **domain** matches the lead's, or its **address/city** does. Same name alone is not enough.
2. A domain that only agrees with itself (a guess from the company name, a legacy row) is not identity: an explicit conflicting street address, city, state or country still refuses. Only an **established** domain (the cited page's own host, or user-confirmed) stands over a conflicting place.
3. The completion score counts contacts and domain points only against a **confirmed** domain (established, or a `domain_check` row recorded after the homepage named the company and agreed on place/address).
4. A date counts as a source date only if it is a **real calendar day** (2026-02-31 is not).

## Live steps (deployed instance, a test account; no sends)
1. Sign in. Open **Plays** and start a scan: *"Independent dental practices opening a second location in New York City"* (a service-area business where a same-name practice exists elsewhere, e.g. a "Smile Avenue Dental" in Pico Rivera, CA). Wait for the scan to finish.
2. Open **Leads**. For each lead, open the details panel.
3. **Expect**: no contact, person, email or phone from another city/state/country is attached. A refused record appears only as a *contact rejected: ...* reason (e.g. `location mismatch Pico Rivera, CA vs New York, NY`, `domain mismatch a.io vs b.com`, `address mismatch ...`). The lead keeps its other evidence.
4. `GET /api/leads?job_id=<id>` (signed in): for each lead, `enrichments[]` must contain no `kind: "contact"`/`"person"` row whose `value`/`source_url` belongs to a different domain than `company_domain`, and every `contact_rejected` row has a `label` of `contact_location_mismatch | contact_address_mismatch | contact_domain_mismatch | contact_location_unconfirmed | contact_unconfirmed`.
5. `GET /api/scan/status?job_id=<id>`: `resolution[]` for a lead with only refused contacts says `contact: "refused"` with `every contact found was refused (...)`.
6. Pick a lead whose `company_domain` was only guessed (no `domain` row with basis `evidence_own_domain`, no `domain_review`): confirm it shows no contact from a record stating another state, and that its evidence score does not count a contact against that domain.
7. Pick a lead whose date is not a real day (rare; the stubbed run covers it): it must not count as "dated".

**Pass** = steps 3-6 hold on every lead of the run. **Fail** = any contact/person/email/phone attached from a different city, state, country or domain than the lead's.
